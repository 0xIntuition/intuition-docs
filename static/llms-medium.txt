# Concept map

A knowledge graph describes entities and the relationships between them. In Intuition, an **atom** represents an entity with exact data bytes, a **triple** expresses a directed relationship, and a **signal** is an economic position associated with an atom or triple.

## Identify the thing and its representation

A recording and an artist are different entities. Each can have a canonical Intuition Identifier (IID), but the protocol's atom ID identifies a particular byte representation. Equal atom data produces the same atom ID; different descriptive payloads can refer to the same IID while producing different atom IDs.

# Protocol writes

Applies to V2 · `@0xintuition/sdk` 4.0.0 · `@0xintuition/protocol` 4.0.0 · `@0xintuition/periphery` 0.1.0 · `@0xintuition/deployments` 0.1.0 · `@0xintuition/cli` 0.1.0

A protocol write changes on-chain state through a signed transaction. Building atom bytes or an action envelope can happen locally; reading a quote needs contract state; submission requires an authorized signer. A prepared request is not a transaction, a transaction hash is not a successful receipt, and a receipt does not prove a Core node has indexed the change.

**Builds on:** [Representation profiles](https://docs.intuition.systems/docs/concepts/representation-profiles), deterministic IDs, vaults, and classifications.

# Representation profiles

Applies to V2 · `@0xintuition/iid` 0.1.0 · `@0xintuition/primitives` 0.1.0

A representation profile describes the atom data that carries an IID. P0 stores the bare canonical identifier, P1 adds the evidence needed to interpret or re-derive it, and P2 adds descriptive fields. The IID names the entity; the atom ID identifies the exact stored bytes, so different representations of one IID can have different atom IDs.

**Builds on:** IIDs and atoms.

**Implemented by:** [iid](https://docs.intuition.systems/docs/reference/packages/iid), [primitives](https://docs.intuition.systems/docs/reference/packages/primitives).

## How it works

The canonical rules are [IID spec §7.2](https://github.com/0xIntuition/intuition-identifier/blob/3e593247c0e7cb168b37368937167ed146d3868a/spec/07-representation-profiles.md#72-the-profiles), [IID spec §7.3](https://github.com/0xIntuition/intuition-identifier/blob/3e593247c0e7cb168b37368937167ed146d3868a/spec/07-representation-profiles.md#73-scheme-typing), and [IID spec §7.5](https://github.com/0xIntuition/intuition-identifier/blob/3e593247c0e7cb168b37368937167ed146d3868a/spec/07-representation-profiles.md#75-requirements).

# Intuition developer docs

Intuition is an identity and knowledge graph protocol. Its packages help applications identify entities consistently, connect them with explicit relationships, and prepare actions through which people signal what they trust.

An **atom** stores a chosen representation as bytes. Its **atom ID** identifies those exact bytes. An **Intuition Identifier (IID)** names the represented entity; the same IID can appear in different representations. A **triple** connects a subject, predicate, and object in that order.

# @0xintuition/atom-enrichment

Applies to V2 · `@0xintuition/atom-enrichment` 0.1.0

Run provider plugins against classified input and collect typed artifacts with provenance. Extraction can turn those artifacts into classification fields; neither operation changes an existing atom's identity bytes.

Use it when you need provider metadata, a selected provider plan, or normalized fields with missing-field diagnostics. Use the IID registry to plan providers before execution. A plan is not a completed lookup, and an artifact is not evidence that every required classification field was extracted.

# @0xintuition/atom-parser

Applies to V2 · `@0xintuition/atom-parser` 0.1.0

## What it's for

Detect and normalize IIDs, text, JSON objects and arrays, URLs, IPFS URIs, addresses, names, and ISBNs into a `ParseResult`. Parsing identifies the input's shape; it does not resolve the entity, assign a canonical classification, or create an atom on-chain.

## When to use it

Use local detection before choosing a classification plugin or asking a reader to confirm an input. Set `remoteFetch: false` for local processing. URL and IPFS inspection is enabled by default, so a parser call is not inherently offline.

# @0xintuition/atom-runtime

Applies to V2 · `@0xintuition/atom-runtime` 0.1.0

## What it's for

A server composition layer for classification and enrichment engines, shared caches, presets, and configuration fingerprints. It does not provide graph storage, worker scheduling, or an automatically offline pipeline.

## When to use it

Use one runtime per intended configuration and application lifecycle to reuse engines and caches. Use the individual parser, classification, or enrichment packages for a single stage. Supplying no graph database removes a persistence prerequisite; it does not prevent selected providers from making requests.

## Install

Use ESM and Promises on Node 20 or newer.

# @0xintuition/classifications

Applies to V2 · `@0xintuition/classifications` 0.1.0

## What it's for

Canonical classification specifications define entity types, recommended fields, identity ladders, and relationship metadata. Creation Profiles package the field labels, schema provenance, predicate IDs, and allowed object targets needed to model a creation form.

## When to use it

Use `/creation/<slug>` for a known creation flow; use root registry helpers for dynamic discovery and validation. A classification slug (`music-recording`), schema type (`MusicRecording`), and display label are different values. Use [primitives](https://docs.intuition.systems/docs/reference/packages/primitives) for identifier-first atom bytes and IDs; filling a field or selecting a relationship never submits a transaction or creates an edge.

IID implements identifier grammar, scheme canonicalization, normalization, recipe hashing, and declarative identity ladders. An IID names an entity; it is not the protocol atom ID of every representation of that entity.
